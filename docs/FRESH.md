# Fresh editor integration

The daemon embeds Fresh's editor library for buffer open, edit, and save. The GPUI client does not link Fresh; it exchanges editor snapshots, bounded pages, and edits with the daemon over ADE.

## Encoding, line endings, and save behavior

Encoding detection, BOM handling, line-ending detection, and serialization use Fresh's daemon-side buffer and save path, so local and SSH sessions apply the same byte conversion. The editor status controls expose the detected encoding/BOM and line-ending style; Save As and Save All use the existing save protocol, while reopen with an encoding, save with an encoding, and line-ending conversion require `editor.file-controls`. All use the shared command registry and authoritative save results. Encoding changes that cannot round-trip the current text without loss are rejected; there is no forced lossy-save option. Reopen with another encoding is available only for a clean buffer. For untitled buffers, choose a destination with Save As before using Save with Encoding. Fresh’s pinned formatter path silently replaces characters that the selected legacy encoding cannot represent, so format-on-save is skipped with a visible save warning for legacy encodings; whitespace cleanup and other on-save actions still run. Unicode encoding saves retain format-on-save. ADE temporarily suppresses the actions inside Fresh’s `Editor::save` finalizer, then invokes `run_on_save_actions` once with capability and encoding guards; Fresh’s finalizer is private. UTF-16 text passes daemon binary screening through Fresh’s encoding detector.

Paged buffers retain Fresh's detected encoding, BOM, and line-ending defaults when saved. Their controls are inspection-only: changing encoding or line endings requires materializing/reopening the file as a normal buffer and is rejected while it remains paged. Paged saves preserve the original byte representation and cannot use conversion controls.

Persistent auto-save is configured with Fresh's `editor.auto_save_enabled` and `editor.auto_save_interval_secs` settings. The interval is taken from the effective Fresh config at daemon editor startup. The GUI timer saves open, dirty, named editor buffers through the same revisioned save pipeline as manual Save, so format-on-save, Fresh on-save actions, `editor.trim_trailing_whitespace_on_save`, and `editor.ensure_final_newline_on_save` still run. The two save cleanup settings are typed Boolean controls and take effect after a daemon restart. Auto-save skips untitled buffers, closed recoverable drafts, and Source Control views, and pauses while disconnected. A save error pauses auto-save for that buffer until the user inspects its state or saves it manually; background metadata refresh retains the visible failure warning. Metadata inspection does not resend buffer contents. Fresh's `hot_exit` and `confirm_quit` settings do not bypass ADE's mandatory dirty-buffer Save / Discard / Cancel guards or daemon draft recovery. Auto-save does not protect edits that have not yet reached the daemon.

## Build setup

Fresh is a pinned git submodule in `vendor/fresh`. Initialize it when cloning:

```sh
git clone --recurse-submodules https://github.com/amirhosseindavoody/fresh-gui.git
```

The daemon crate depends on `fresh-editor` with its `runtime` feature. Fresh's web UI, GUI, and plugins are not part of the desktop host. The daemon runs Fresh's `!Send` editor on its own thread and sends editor operations to that thread.

To update the pin, check out the desired commit in `vendor/fresh` and update `vendor/fresh.rev` to the same SHA. The package recipe uses that revision when the submodule is unavailable.

## Runtime boundary

Fresh provides the editor buffer and save behavior. `fresh-gui` provides the ADE protocol, client connection, PTYs, file explorer sandbox, workspace state, and GPUI rendering. Normal editor views continuously send revisioned range transactions when the daemon advertises `editor.range-edits`. The existing `BufferEdit` full-text CAS path remains available for older peers; the protocol version stays `0.4.0`. Saving writes through Fresh after pending transactions have been acknowledged.

Language servers use the same daemon-side Fresh `LspManager` and its local Authority. The worker pumps Fresh's editor tick, applies ADE edits through Fresh events so servers receive `didChange`, and closes Fresh buffers so they receive `didClose`. The GUI's `lsp` configuration is passed into Fresh before editor construction; the ADE bridge polls merged diagnostics and carries explicit format requests/results. Server commands resolve on the daemon host, including when a Windows GUI connects to a Linux daemon. Built-in Fresh LSP defaults are not started by Fresh GUI unless configured in its `config.json`.

Problems aggregates diagnostics from open editor buffers in the active workspace. Severity and source filters apply to the list; clicking a problem reveals its range, related information can navigate to another location, and **Quick fix…** requests code actions through the workspace-edit flow. F8 / Shift+F8 cycle errors across those open buffers. Diagnostic ranges are retained for navigation and interaction; the editor uses GPUI Kit's existing underline and hover presentation rather than adding custom gutter markers. Closed files and project-wide pull diagnostics are not included.

Formatting requests preserve Fresh's provider semantics: an active selection prefers LSP range formatting when advertised; otherwise the language's configured external formatter runs on the document. Document LSP formatting is the fallback when no external formatter is configured. A configured external formatter that is missing or fails is an error, not a reason to silently use the fallback. Document formatting and selection formatting are applied through the existing revisioned #141 edit path. `format_on_save` runs configured external formatters and Fresh on-save actions for full buffers; it does not invoke LSP format-on-save. Paged buffers skip formatting and format-on-save. On-save actions run only for clients negotiating `lsp.controls`, since those clients reconcile the authoritative save snapshot. A failed post-save action still acknowledges the written disk generation and carries a warning; any remaining unsaved formatter output stays dirty and recoverable. Timed-out LSP formatting replies are discarded before Fresh can apply them to newer edits.

The additive `lsp.controls` capability gates selection-format and language-server lifecycle requests, keeping the protocol version unchanged and older-daemon handling explicit. Status, Start, Stop, and Restart operate on the active buffer's language through Fresh's manager. Stop disables automatic start for that language's current runtime server set; Start and Restart honor each server's configured enabled flag and the global `lsp_enabled` setting. Settings expose per-language entries and enable flags. Reload Config preserves project/session LSP disables resolved for the daemon startup directory. Logs are bounded by language and displayed without server identity because Fresh's window notifications omit it; when a daemon window has buffers from multiple workspaces, ambiguous logs and progress are withheld rather than attached to the wrong workspace. There is no separate server-specific stderr reader.

The additive `lsp.requests` capability carries generic revision-aware completion, hover, signature-help, and completion-resolve requests through that same `LspManager`. A metadata operation polls the routed servers’ advertised completion trigger characters, including changes after initialization. The pinned Fresh capability summary retains signature-help support but omits its trigger characters, so automatic signature help uses `(` and `,` for eligible servers; manual invocation remains available. Each request identifies its buffer, view, request ID, base revision, UTF-8 byte offset, feature, and optional trigger character, completion item, or server route. Fresh converts the offset to its LSP position and applies per-feature server routing; responses aggregate asynchronously by request ID and identify each responding server; a five-second deadline returns available replies and cancels outstanding ones. Cancellation is forwarded when supported, and the daemon checks revisions and marks out-of-date replies stale. Older daemons leave provider hooks disabled; manual invocation reports the missing capability. Requests are also disabled for paged buffers: the public Fresh providers require a complete document, while GPUI Kit 0.6.6 has no range-backed provider hook, so querying would materialize the large file.

Fresh’s editor request handlers are crate-private, so ADE thin-wraps public `LspHandle::send_plugin_request` and intercepts its `PluginLspResponse` events. The manager retains Fresh's original runtime, Authority, and per-window `AsyncBridge` inbox. ADE separates the public window dispatch queue from that inbox, filters GUI replies, and forwards unrelated messages to Fresh's dispatcher, including during formatting. This prevents the editor tick from consuming GUI replies while preserving Fresh's server lifecycle. For normal buffers, the client implements gpui-component’s public `CompletionProvider` and `HoverProvider` hooks for its existing native popups; signature help is shown in the editor's signature bar. Completion routes all supplied `textEdit` and additional auto-import edits through the existing #141 range-edit transaction, so the change is one Fresh undo unit. Public Fresh snippet defaults and choices are honored and `$0` sets the final cursor position; snippet tab-stop navigation is not provided. Initial popup behavior does not lazily request `completionItem/resolve` or invoke completion commands, although the generic request bridge includes completion-resolve plumbing for future use.

When no server is eligible for completion, ADE reuses Fresh's public `BufferWordProvider` with a bounded scan window and standard identifier boundaries. Fresh supplies smart-case matching and proximity/frequency ranking; no separate completion-word index is maintained in the GUI.

## Quick Finder and navigation

`Ctrl+P` opens a single native finder. With no prefix, it recursively searches files under the active workspace root using Fresh's public `FuzzyMatcher` and the daemon's existing gitignore-aware walker. A 120 ms client debounce avoids starting a scan for every keystroke; each new query cancels the previous daemon scan. The daemon returns a final ranked list capped at 200 paths, with no incremental results or reusable file-list cache yet. The client reuses the pinned Fresh fuzzy matcher source through a small shared module for command and open-buffer ranking, because the desktop host intentionally does not link `fresh-editor`.

Use `>` for registered commands, `@` for open buffers, and `:line[:column]` for a live preview in the current editor. Escape restores the starting cursor; confirming the preview records the location jump. `path:line:column` opens a file at a location. Absolute paths, relative paths containing `/`, `.` or `~` prefixes, and directory paths open or complete directly before recursive enumeration finishes. Arrow keys move through results, Enter or a click opens the selection, and Tab or Right completes the current path. On an older daemon without `project.file-finder`, the finder reports that recursive search needs an upgraded daemon; direct path and directory opening remain available.

Commands and native shortkeys use the same descriptor registry, including focus-context and negotiated-capability filtering. The namespaced registration API is the intended extension point for plugin commands, but plugin command execution is not implemented yet (#158). The `:line[:column]` preview requires a fully loaded buffer, so paged files cannot use it. The ADE action bridge currently exposes undo/redo; Fresh's matching-bracket and bookmark navigation are not connected to native views, with bookmarks deferred to the separate #155 bridge.

Confirmed file, open-buffer, and line jumps join definition and symbol navigation in the existing bounded, in-memory history per client window and workspace. Back/forward retains view identities across pane changes; this history is transient and does not change the last-selected terminal directory used by Explorer and Source Control. Manual GUI and Windows-to-Linux SSH testing for the finder has not been performed here.

## In-buffer search and replace

`Ctrl+F` opens incremental find; `Ctrl+R` opens the replace toolbar. `F3` and `Shift+F3` move to the next and previous match. The toolbar shows the current match and count, highlights matches, and can clear the highlights. The **Query Replace** command opens the replace toolbar; its **Query replace** button starts a review. Review starts at the current match and wraps once. For each snapshotted match, `y` accepts, `n` skips, `!` accepts all remaining, and `q` or Escape ends review. Decisions are deferred: the draft stays unchanged while review is active, then accepted replacements are committed together as one `editor.range-edits` transaction and one Fresh undo group. Cancel commits earlier accepted replacements. Save and close/recovery guards also finalize accepted decisions through the existing edit and recovery path. Editing is disabled during review, and a stale review is discarded if its text changes.

Search preview is daemon-side and read-only. The client sends its exact current draft, query, options, and optional scope over the additive `editor.search` capability; replacement is enabled only when range edits are negotiated and the preview still matches the acknowledged draft. Older daemons without `editor.search` show an upgrade error; replacement also requires `editor.range-edits`. The client does not silently fall back to different matching semantics. ADE includes Fresh's pinned `app/regex_replace.rs` helper source because Fresh marks that module private. This reuses Fresh's literal/regex construction, Unicode regex behavior, whole-word boundaries, capture expansion, and replacement escapes without changing the vendor pin. Regex replacements expand `$1`, `${name}`, and Fresh's `\n`, `\t`, `\r`, and `\\` escapes; invalid regexes appear as inline errors.

gpui-kit 0.6.6 already supplies an input-editor search panel and `SearchMatcher`: incremental literal matching, a case toggle, match highlighting/count, next/previous navigation, replace-current, and replace-all. It uses ASCII-only case-insensitive matching and does not support whole-word or regex search, Fresh capture/escape replacement, query-replace review, per-workspace option persistence, or selection-limited search. Selected text only pre-fills the query. The standalone Fresh-backed GUI editor uses ADE preview and its own toolbar while retaining GPUI decorations and controls.

Search covers the whole loaded buffer by default. The **Selection** option uses the selection captured when the toolbar opened as a fixed byte range; later cursor changes do not move the scope. Disabling it returns to the whole loaded buffer. For paged large files, search is limited to the loaded page, shown in the match count, and page navigation resets selection scope. Whole-file scanning is deferred to daemon-side project search. Paged undo/redo remains unavailable, as documented for #144 below; page replacements still use the existing Fresh transaction path. Replacements that exceed the existing 2 MiB buffer or 64 KiB page edit limit are rejected before the draft changes. Preview is bounded to an 8 MiB draft, an 8 MiB replacement output budget, and 10,000 matches; if the match cap is reached, replacement is disabled so a partial preview cannot be mistaken for replace-all. Search queries, replacement text, and selection scope are never persisted. The search actions can be remapped through the #151 keybinding editor. Case, whole-word, and regex choices are saved only after an intentional toggle, in the existing workspace layout record. **Reset options** removes that workspace override and restores defaults.

Manual GUI and Windows-to-Linux SSH testing for search has not been performed here.

`lsp.navigation` adds navigation features to the same revision-aware request bridge. Fresh's `handles_for_feature` chooses definition, implementation, references, document-symbol and workspace-symbol routes; replies include normalized Location/LocationLink and nested DocumentSymbol destinations with selection positions and symbol names. Declaration and type-definition requests use Fresh's definition route because its pinned capability summary has no distinct declaration/type-definition fields; a server that does not support the method reports an error. Workspace searches query servers eligible for the active editor's language, rather than launching servers for unopened languages. URI-only workspace symbols that need `workspaceSymbol/resolve` are not resolved yet.

Fresh's TUI request handlers and PositionHistory are tied to its local editor buffers and windows. The GUI therefore uses a native Command picker and a portable, bounded byte-location history while reusing the existing request/cancellation bridge. A selected opaque URI travels through `EditorOpenLocation`; Fresh decodes the URI on the daemon, the existing editor path enforces path authorization and buffer ownership, and the reply supplies the absolute byte offset. Large destinations use paged opens and bounded Fresh reads. History is per client window and workspace, retains view identities across pane changes, and reopens closed named files through the same editor path. It is not persisted across client restarts.

## Project search and replace

**Search in Workspace** runs on the daemon over the explicit active workspace root. It does not use the last-selected terminal's directory. The daemon's Fresh-compatible search helper supplies the same literal, whole-word, regex, and replacement expansion behavior as in-buffer search. The adapter uses the `ignore` crate already used by Fresh to honor hidden files and `.gitignore`, `.ignore`, global excludes, and parent ignore rules by default; **Include ignored** opts into those paths. Include globs further restrict paths. Results stream by file group and can be cancelled. The native result panel previews each match, opens its exact UTF-8 byte range, and supports selecting a whole file or individual matches for replacement.

Open buffers, including dirty and recoverable drafts, are authoritative over disk and are replaced through revision-checked Fresh edits, so a stale preview cannot overwrite newer draft text. Unopened files are edited on the daemon only after disk-generation conflict checks. The scan is bounded to 2 MiB per file and 2,000 matches; replacement review snapshots are capped at 32 MiB, with a 1 MiB result payload per file. Files larger than 2 MiB, including paged buffers, are skipped with a warning. Files containing NUL bytes or invalid UTF-8 are skipped; project search is text-only. Older daemons without `project.search.v1` show an explicit unsupported-daemon message. Search criteria and result selections are transient. Source Control diff views still use their existing save-time synchronization; save or close dirty diff drafts before project search. An older recovery copy whose source is already open is preserved and reported for explicit recovery, so searching cannot replay it over a newer draft.

Fresh’s pinned `live_grep.ts` and `git_grep.ts` expose grep through the plugin/TUI runtime, without a Rust project replacement service for ADE. The adapter therefore owns daemon enumeration and review snapshots, reusing #148’s unchanged Fresh regex/replacement module and #141/#142/#143’s transactions, recovery and save guards. Replacements are one undo group per open file; a multi-file batch reports failures per file and is not atomic across files.

Manual GUI and Windows-to-Linux SSH validation for project search has not been performed here.

## Rename, code actions, and workspace edits

The additive `lsp.workspace-edits` capability sends `textDocument/prepareRename`, `textDocument/rename`, `textDocument/codeAction`, `codeAction/resolve`, and `workspace/executeCommand` through Fresh's public `LspHandle::send_plugin_request` bridge. The same `LspFeature` routing and capability filters used by Fresh's typed request methods choose the servers; the existing ADE bridge preserves response IDs and server attribution. Rename is routed to the first eligible Fresh server and the response remains tied to that server. Code actions fan out through Fresh's merged-feature routing and retain server identity so resolve and command execution target the provider. The GPUI client uses F2 for rename and Ctrl+. for code actions. Fresh's own TUI popup and `apply_workspace_edit` are not reused: the popup is TUI-specific, while the editor-side workspace edit applier is crate-private and applies files sequentially. ADE owns authorization, revision checks, preview, and filesystem staging on the daemon.

The daemon caches each server-returned edit behind an expiring, single-use token. The proposal builder checks versioned edits against Fresh's per-server document versions. Applying rechecks those versions, open-buffer revisions captured when the request started, and #143 disk generations captured at the reply for all targets. Unversioned closed-file edits use the reply's observed disk contents as their baseline; a server that omits versions cannot prove that its edit was computed from that same disk content. Open buffers go through the #141 range-edit path, preserving one undo group per buffer; the edited dirty text is checkpointed through the existing draft path before publication. Closed-file operations reject paths held by recovery drafts in any workspace, including detached workspaces. Closed text files must be regular UTF-8 files at most 2 MiB. A transaction is limited to 64 files and 8 MiB total. Closed-file changes are staged with rollback on reported failure. Open buffers remain dirty until explicitly saved; closed text changes are written immediately after confirmation. Undo is per open buffer; there is no workspace-wide undo for closed-file or resource edits. Resource create, rename, and delete operations are accepted only for closed regular files; overwrites, directories, symlinks, and paths held by open buffers or recovery drafts are rejected. Every edit is previewed before the user applies it, including edits spanning multiple files.

Fresh's server-initiated `workspace/applyEdit` callback has no delayed-reply hook for waiting on the user's preview decision. Those requests are intercepted and previewed, but Fresh has already acknowledged them on the LSP wire, so that acknowledgement can say applied before the user accepts. The callback also omits server identity; a versioned edit can be checked when it is tied to one pending ADE command, otherwise it is rejected. Ambiguous workspace ownership is rejected explicitly. Filesystem staging rolls back on reported errors, but it cannot provide crash-atomic multi-file replacement or prevent races with external writers; rollback failures report the affected paths. Rename, code actions, and workspace edits are unavailable for paged buffers. Manual GUI and Windows-to-Linux SSH testing has not been performed here.


## Settings and keybindings

The native Settings window edits three distinct sources. Local client presentation is saved on the machine running GPUI, in `fresh-gui/config.json` (`$XDG_CONFIG_HOME/fresh-gui/config.json` on Linux, `%APPDATA%/fresh-gui/config.json` on Windows, or `~/.config/fresh-gui/config.json` otherwise). It overlays the daemon's `HelloUi` values for that client only. Its full JSONC document can be edited in the Settings window. Fresh configuration and shell/keybinding settings are saved on the daemon host in the daemon's user config file; **Edit JSON** opens that file in the daemon's configured file editor. Workspace Fresh settings are saved to `<workspace-root>/.fresh/config.json`; host UI, terminal shell, and shortkeys are rejected in that layer. Over SSH, daemon and workspace reads/writes are performed by the daemon, while local presentation settings stay on the connecting client.

The settings catalog reuses `fresh::config::Config::default()` for Fresh defaults and validates Fresh layer documents through `fresh::partial_config::PartialConfig`. Daemon settings are applied using Fresh's `PartialConfig` merge semantics. At startup, the Fresh session and project layers for the daemon's startup directory take precedence over daemon user settings. ADE keeps its lazy-file threshold at the negotiated snapshot boundary after merging those layers. The catalog exposes a currently selected set of Fresh fields as native controls, including line numbers, wrapping, wrap column, tabs, tab size, auto indent, auto close, and auto surround; it is not a complete mirror of Fresh's schema. Line numbers and wrap column are marked as Fresh view settings whose native renderer mapping is still pending; ordinary native typing retains GPUI Kit indentation and pairing behavior; explicit Fresh commands use the daemon’s resolved smart-editing settings. Typed changes patch the JSONC syntax tree, retaining comments and unrelated or unknown data. This uses a custom native editor because Fresh's settings model and modal are built for Fresh's own terminal view, and Fresh's file save path rewrites JSON rather than preserving JSONC comments.

Native shortkeys use the daemon config's `shortkeys` list, with one-key capture, search, action editing, focus contexts, and context-aware conflict checks. Chords can be entered as text; conflict detection checks overlapping chord prefixes. Fresh editor keybindings are a separate `keybindings` / keymap model; Fresh's existing editor includes key recording, context-aware conflict checks, chord support, plugin commands, and modes, but its view/input flow is terminal-specific. The current native editor exposes native shortkeys rather than presenting Fresh's full keymap editor. Shortkey updates reload live. Daemon `editor.line_wrap` maps to native wrapping live unless a local `ui.editorLineWrap` override is set. Other Fresh engine config values are saved for Fresh's next daemon/editor startup; the current Fresh editor instance is not rebuilt in place. Workspace config is loaded for the daemon startup directory and is not re-resolved when changing active workspaces.

The daemon can run without the editor using `--no-editor`; terminal and filesystem features remain available. See [Architecture](./DESIGN.md) for process boundaries and [WORKSPACES.md](./WORKSPACES.md) for workspace behavior.

## Draft recovery

Fresh's pinned recovery service provides periodic hot-exit saves, chunked recovery records, crash detection, and atomic recovery-record replacement. ADE uses the daemon-owned workspace draft store for GUI recovery because recovery must checkpoint every accepted edit, preserve stable GUI untitled identities, expose explicit list/restore/discard operations, and retain complete draft text when the original file is missing or changed. Those protocol semantics do not match Fresh's normal startup crash prompt or its file-chunk reconstruction path. The store writes through a temporary file and rename; it never writes draft text to the working file. Fresh still owns buffer editing and normal saves. Fresh's normal local saves use atomic writes except when ownership requires an in-place write; remote saves use Fresh's remote filesystem path.

## Edit transactions and actions

The bridge uses the pinned Fresh revision `14f7d28b7ab1` without changing it. `Editor::log_and_apply_event` applies an `Event::Batch` containing `Delete`, `Insert`, and `MoveCursor`; Fresh owns the event log, inverse events, atomic undo groups, buffer side effects, and LSP notifications. `Editor::handle_undo` and `handle_redo` execute actions on the explicitly selected buffer. The bridge does not maintain another undo stack.

`BufferRangeEdit` carries a buffer ID, client view ID, base revision, ordered replacement ranges, and the post-edit primary selection. `BufferAction` carries the same identities, base revision, and pre-action primary selection. All ranges and selections are **UTF-8 byte offsets**, on scalar boundaries; ranges are half-open and each range indexes the text after preceding ranges. GPUI Kit 0.6.6 exposes byte-based `cursor()` and `selected_range()`, so these positions already match Fresh. LSP diagnostic columns and `didChange` positions are **UTF-16 code units** from the line start, converted by Fresh; emoji and CJK are covered by bridge tests. Other existing line/column fields retain their documented conventions.

Fresh's pinned batch LSP collector calculates sub-event positions against the original buffer. The worker therefore validates the entire ordered transaction first, then translates its net effect into one contiguous range replacement. This makes the delete/insert coordinates correct both for Fresh and for LSP's sequential change arrays, including undo/redo. It can replace the unchanged text between distant edits; a public Fresh remote-transaction API with sequential position conversion would allow finer multi-range notifications later.

The client coalesces changes over a fixed 75 ms window, with at most one outstanding transaction per view. The timer does not restart on every keystroke. Later typing stays in the visible draft and is diffed against the last acknowledgement. Save, format, undo, and redo flush preceding changes and wait for their replies. Native GPUI remains responsible for ordinary text input and presentation; negotiated undo/redo and smart-editing actions use Fresh's history.

The worker observes Fresh's current text before revision comparisons, including asynchronous formatting. A stale transaction returns `BufferEditResult` with `accepted=false`, current revision, text, selection, Fresh modified state, and both identities. `BufferSync` fetches the authoritative state after a transport reconnect; periodic state polling also reconciles server-originated changes. The reusable client `EditSync` holds the acknowledged base, sent text, and a divergent server snapshot. It keeps the local draft when both sides changed, pauses automatic writes, and lets the user choose **Keep my edits** or **Use server text**. Clean views adopt server changes. A lost acknowledgement can be recognized by comparing the snapshot to the exact text sent.

External disk changes use the `editor.external-changes` capability and the same daemon-owned Fresh editor for local and SSH workspaces. For snapshot-sized buffers, every 350 ms the daemon compares each open path's modification time, size, and content hash, which catches atomic replacement and same-metadata writes. For a clean buffer it calls Fresh's `Editor::handle_file_changed`, reusing Fresh's normal file watcher and auto-revert path. When Fresh's mtime check does not observe a content change, the worker applies a delete/insert batch with `log_and_apply_event` and marks it saved; this event path preserves Fresh's undo history. Dirty buffers are never changed by the watcher: the daemon sends both its retained buffer text and optional disk text, and the GPUI editor offers **Compare**, **Reload**, and **Keep**. Compare opens the existing read-only split diff. Reload explicitly discards the draft; Keep retains it and marks it as diverged. If a save finds the disk generation changed since load, it returns the same review notice instead of writing; the user can explicitly choose **Overwrite disk** for that generation. Resolution requests include the buffer revision and disk generation, and the daemon rechecks both before acting. Deleted clean files become recoverable drafts, while unreadable, non-UTF-8, or oversized files are not treated as deletions and cannot be silently saved over. The existing 2 MiB snapshot limit applies. Polling coalesces identical generations; the final fingerprint check and filesystem write cannot be one atomic transaction against uncooperative external writers.

Fresh's `handle_file_changed` auto-revert path resets Fresh's undo history. The event-batch fallback can preserve it. The GPUI public text setter used for an explicit Reload clears GPUI Kit's local undo state; the client maps the primary selection through authoritative text replacements and restores the scroll offset with GPUI Kit’s public `set_scroll_offset` API. For older daemons without `editor.external-changes`, client-side snapshot reconciliation still protects dirty text, but there is no daemon generation notice or safe overwrite detection.

## API boundaries and follow-ups

Fresh already exposes the event and undo APIs needed for this bridge. The additive `editor.smart-editing` capability routes explicit editor commands through Fresh actions and returns their authoritative text and primary selection. Older daemons do not advertise these commands. The client reuses Fresh for selection expansion, word/line selection, smart Home and Backspace, newline/tab/dedent, bracket matching, surround, line duplication/deletion, comment toggle, sorting, and case conversion; command entries use the shared registry so the palette and keybinding editor can find them. Fresh's `MoveLineUp` and `MoveLineDown` actions also reorder lines through that event pipeline. The pin has no unique-line action, so unique-line filtering is computed in the daemon and applied through the existing revisioned range-edit path as a single Fresh history transaction. Newline, Backspace, and Surround are explicit commands, while ordinary character input stays in GPUI Kit. A small allowlisted adapter dispatches Fresh actions because the pinned public dispatcher exposes its full action dispatcher only for tests; the vendor pin is unchanged.

GPUI Kit already owns native Alt-click cursors, Alt+Shift column selection (Ctrl+Alt column dragging on Linux), Add Cursor Above/Below, and coordinated typing across those carets. Native auto-pairing and smart indentation keep their GPUI configuration. Fresh's `auto_indent`, `auto_close`, and `auto_surround` settings apply to Fresh-routed smart-editing commands. Explicit surround commands reject disabled or unsupported delimiter rules without replacing selected text. Markdown disables auto-close and auto-surround in the pinned defaults; enable `languages.markdown.auto_surround` in daemon/workspace JSON and restart the daemon to use those surround commands. Fresh remains the single edit history for daemon actions, undo, and redo.

Two selection limits remain: add-next/all-occurrences matching is unavailable because GPUI Kit 0.6.6 has no public multi-selection setter, and full selection-vector or rectangular-selection restoration across undo, formatting, and authoritative text replacement is incomplete. Fresh action requests currently carry the primary selection. Ordinary acknowledgements must preserve GPUI's secondary carets; replacing text through the public setter resets them. A stable public `apply_remote_transaction(buffer, view, edits, selection)` facade would avoid active-buffer switching and expose richer view/multi-cursor semantics. View IDs correlate requests and replies; they do not create independent Fresh splits. The SCM split diff editor retains its existing full-text save path; the continuous action bridge and native external-change resolution bar currently apply to normal editor tabs. Dirty SCM diffs remain visible on disk changes, and daemon save-conflict checks refuse an implicit overwrite; open a normal editor to resolve the external change.

This bridge retains current live editor views during a transport reconnect. Persistent draft storage and close/restart recovery are described in [WORKSPACES.md](./WORKSPACES.md). Untitled drafts remain visible but paused after reconnect until a safe daemon buffer reattachment is available. Manual native GUI and Windows-to-Linux SSH sessions, including settings edits, are not exercised by the automated tests.

## Large files

The Fresh pin remains `14f7d28b7ab1`. The daemon sets Fresh's lazy-file threshold at the 2 MiB snapshot boundary. ADE negotiates `editor.paged-reads` without changing protocol version `0.4.0`: `BufferPaged` supplies metadata, `BufferRead` requests a byte range, and `BufferPage` returns revisioned text and the actual UTF-8-aligned start offset. Responses contain at most 64 KiB of text. The native editor normally requests 32 KiB, leaving room for insertions up to the 64 KiB edited-page limit. Opening metadata contains no file text. An older client gets a capability error before opening an oversized file; ordinary snapshots and edits remain compatible with older daemons. The client's full-snapshot convenience helper reports an explicit error for a paged open.

Fresh's `Buffer::get_text_range_mut` faults in piece-tree chunks; `total_bytes` reports file length without a line scan. UTF-8 reads include whole code points around requested boundaries, with the returned start describing their actual byte origin. GPUI Kit 0.6.6's editor expects a complete Rope and has no external range-provider hook. Each GPUI editor therefore holds a single page, with Previous/Next and a zero-based byte jump. Scrolling, selection, highlighting, and Find work within that page; line numbers start again on each page. Page navigation waits for pending revisioned edits before replacing text, and page reads disable input until their reply arrives. Markdown preview and document formatting are unavailable for paged files.

`BufferRangeEdit` is the existing #141 transaction, with an optional viewport and global UTF-8 offsets. The daemon validates all ordered replacements and the selection against a bounded working page before applying a net `Event::Batch` through `Editor::log_and_apply_event`. A stale revision returns the authoritative page and retains the local draft for explicit conflict resolution. Save waits for accepted edits, then uses Fresh's copy/insert save recipe. The pinned `StdFileSystem` inherits a default `write_patched` that flattens this recipe into a full `Vec`; ADE thin-wraps that one operation with a 64 KiB streaming copy loop, a private same-directory temporary file, permission preservation, fsync, and rename. All other filesystem operations delegate to Fresh's `StdFileSystem`, and Fresh still constructs the recipe and finalizes its saved piece tree. Full-text replacement, full-buffer sync, and undo/redo actions explicitly reject paged buffers in this version.

Paged drafts extend the existing atomic workspace `DraftStore`, in separate `*.paged.json` records that older daemons cannot mistake for empty full-text snapshots, with the source generation, encoding/line-ending metadata, and ordered viewport transactions. A checkpoint contains edits, not a copy of the source. Fresh's public `get_recovery_chunks` lacks replaced source lengths, so it cannot reconstruct ADE deletions/replacements; this small journal is required for revisioned GUI recovery. Journals are capped at 4 MiB of inserted bytes plus edit metadata between saves. Exceeding the budget rejects further edits before mutation; Save releases it. Restore preserves the journal and refuses replay if the source generation differs or the file is missing. Detected external changes also block reads, edits, Save, and Save As, because unloaded pieces still depend on the original backing file. The GUI never installs the empty legacy notice as page text or offers unsafe overwrite/reload for that file.

Known limits and follow-ups for #144:

- Client page storage and each transfer are bounded. Fresh retains faulted-in chunks and has no public general eviction API at this pin; daemon resident memory can grow with visited regions. The 4 MiB journal budget also does not bound Fresh's undo history. A bounded daemon cache needs a reviewed Fresh API extension.
- A page can grow to at most 64 KiB; oversized paste/edit transactions are rejected and retain the local draft. Remove the excess and use Retry sync. Buffers initially opened in snapshot mode retain the 2 MiB edit cap; automatic conversion while typing is deferred.
- Continuous scrolling across page boundaries, whole-file search, optional line-index scanning, scan progress/cancellation, and paged undo/redo are deferred. Fresh already provides `search_scan_init` / `search_scan_next_chunk`, `prepare_line_scan` / `scan_leaf`, and progress state; these need a later ADE/UI bridge.
- Paged saves requiring another file owner's in-place write or sudo fallback are rejected; use Save As to a new owned path. Fresh's pinned fallback materializes Copy operations and cannot preserve the bounded save guarantee.
- Large-file generation guards use size, nanosecond modification time, and device/inode on Unix. They avoid scanning all source bytes during open/poll/read; same-metadata in-place writes and the race between checking and I/O remain limitations. Changed-source journal recovery needs a stable backing snapshot or upstream source-generation support.
- Sparse multi-gigabyte fixtures contain NUL holes and are rejected by the existing binary-file gate. The automated 3 GiB fixture verifies that explicit binary rejection; this PR does not claim native text editing parity for those fixtures. Non-sparse multi-gigabyte files have not been measured.
- Manual Linux/Windows GUI and Windows→Linux SSH testing was not possible here. A side-by-side Fresh TUI comparison was not run. Automated tests exercise the same daemon authority and protocol used over SSH, plus the Windows compile target.

### Reproducible measurement

Run the ignored harness through the project's pixi environment (debug profile, long-line ASCII fixture):

```sh
export PATH="$HOME/.pixi/bin:$PATH"
CARGO_BUILD_JOBS=4 LARGE_FILE_MIB=100 pixi run -- cargo test --locked -p fresh-gui --test editor_paged measure_large_file_open_range_edit_and_daemon_rss -- --ignored --nocapture
```

It creates the fixture in 1 MiB writes, records daemon start-to-health latency, open metadata latency, a range read, an incremental edit acknowledgement, streaming save latency, full-duplex serialized JSON bytes for the editor exchanges, and daemon `/proc` VmHWM after save. It verifies every saved byte using a bounded read buffer. Editor latency excludes daemon startup/handshake, WebSocket framing, GUI rendering, and the client's 75 ms edit-coalescing interval. Startup timing includes the harness's 50 ms health polling interval. Warm filesystem cache and debug builds affect these numbers; they are a reproducible smoke measurement rather than a Fresh parity performance claim.

Measured on this Linux x86-64 box on 2026-09-30 (8 Xeon vCPUs, 15 GiB RAM, debug profile, warm file cache). Each row starts a new daemon:

| Fixture | Daemon start → health | Open metadata | Range read | Edit acknowledgement | Save | Duplex JSON bytes | Peak daemon RSS |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 3 MiB | 68.007 ms | 45.781 ms | 14.620 ms | 13.374 ms | 9.992 ms | 99,974 | 50,760 KiB |
| 100 MiB | 76.301 ms | 44.814 ms | 16.776 ms | 27.043 ms | 256.994 ms | 99,990 | 53,064 KiB |

Both read payloads were 65,536 bytes; edit replies contained the 32 KiB working window. For 100 MiB, stage high-water RSS was 48,616 KiB after startup, 50,448 KiB after open, 52,200 KiB after read, and 52,456 KiB after edit. Peak RSS includes save. This does not establish bounded RSS after scrolling through all file chunks.

The measurement caught the pinned local filesystem's flattening save path: before the streaming adapter, 100 MiB save peaked at 205,048 KiB. The final adapter reduced it to 53,064 KiB. This is a comparison of daemon adapter implementations, not a Fresh TUI comparison. The 3 GiB sparse fixture was exercised separately and returned `binary_file`, without editing or saving it.
